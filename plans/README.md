## Found during execution (not by the audits)

Things the executors surfaced that no audit pass caught. Recorded because they
are the kind of finding that only appears when someone actually changes the
code.

- **BUG-12 (latent, agenda grids).** `computeRange` in
  `src/components/dashboard/agendaCalendarShared.tsx` accumulates with
  `Math.min(earliest, timeToMinutes(...))`, so ONE malformed time value
  (`timeToMinutes("")` is `NaN`) poisons the whole range: `buildHourLabels`
  emits nothing and every `topPx`/`heightPx`/`gridHeightPx` becomes NaN, i.e.
  the entire day/week grid breaks. `WeekGrid.computeViewportRange` does the
  same job with `if (s < earliest)`, which skips the bad entry and renders the
  rest. Reproduced in node: same two entries yield `NaN NaN` vs `480 540`.
  This defeats `normalizeTime`'s stated defensive intent (its comment says it
  degrades to `""` precisely to avoid "white-screening the whole page").
  RESOLVED inside plan 006: the shared helper standardizes on the robust
  skip-non-finite form, with a test pinning it.
- **Extra month-table copies.** `src/components/common/MonthGridPopover.tsx:31`
  and `src/components/common/PeriodPicker.tsx:82` each carry a local
  `MONTH_SHORT_SR`. Out of plan 006's scope (they contain no `"januar"`, so
  they pass its verification grep). A follow-up should fold both into
  `src/utils/serbianCalendar.ts`.
- **kid_set_theme still grants EXECUTE to `anon`** (found while writing plan
  012's migration). Its migration's `REVOKE ALL ... FROM PUBLIC` did not undo
  the `anon` grant that `ALTER DEFAULT PRIVILEGES` hands out at creation time,
  so the ACL reads `{postgres=X,anon=X,authenticated=X,service_role=X}`.
  Harmless in practice - the body filters on `auth.uid()`, which is NULL for
  `anon`, so the UPDATE matches no row - but the same trap is why plan 012's
  new RPC revokes from `anon` and `authenticated` BY NAME. Worth a one-line
  cleanup migration.
- **`families` cannot share `broadcast_family_change`** - the function reads
  `NEW.family_id` and `families` has no such column (proven by the actual
  error, not assumed). Plan 012 gave it a dedicated
  `broadcast_families_change()` rather than making the shared function branch
  on `TG_TABLE_NAME` and taxing every write to 25 tables.
- **Plan-authoring lesson: `oxlint -D <rule>` silently ignores unknown rule
  names**, so "no output" does not prove a rule is active. Verify a rule fires
  with a deliberate violation before trusting a zero-violation measurement.
- **Plan-authoring lesson: `pnpm test -- <name>` does not filter** (vitest
  receives the `--`). Use `pnpm vitest run <path>` in plan command tables.

### Security (SEC)

- **SEC-01 -> plan 008 (P0).** `profiles` self-update policy has no `WITH CHECK`
  and no column restriction (`20260130000000_initial_schema.sql:99`), and is
  never dropped. Any member can set their own `is_admin = true` or rewrite
  their own `family_id` (which moves their entire data scope). No guarding
  trigger exists. `kid_mode.sql:209-212` already names this policy as the
  too-broad shape not to repeat.
- **SEC-03 (HIGH).** `update-user-email` changes a verified identity with no
  reauth and accepts kid-session JWTs; `email_confirm: true` skips
  confirmation and the old address is not notified. A kid session can
  desync `auth.users.email` from `kid_access.login_email`, permanently breaking
  the parent's device-removal control. Password change DOES reauth
  (`PasswordCard.tsx:67-71`), so the asymmetry looks unintentional.
- **SEC-04 (MED).** `notify_on_list_create` trigger has no `WHEN` clause on
  `scope`, so creating a PERSONAL list pushes its title to every family
  member's lock screen - the exact audience `scope = 'personal'` exists to
  exclude. Verified: trigger is `FOR EACH ROW` with no scope guard.
- **SEC-05 (MED).** `receipt-import` validates the host allowlist correctly but
  fetches with `redirect: "follow"` and never re-validates after a redirect;
  response body read with no size cap.
- **SEC-06 (MED, conditional).** Six functions decode the JWT `sub` without
  verifying the signature, relying entirely on `config.toml` absence from the
  `verify_jwt = false` list. One config mistake turns `manage-family-login` /
  `kid-access` into unauthenticated admin endpoints.
- **SEC-07 (MED).** `manage-family-login` disable path never tears down
  `kid_access`/`kid_devices`/`kid_invites`, so "Ugasi nalog" leaves a working
  kid credential; the reverse guard exists in `kid-access` but not here.
- **SEC-08 (LOW).** `google_connections.family_id` is frozen at OAuth time and
  never re-derived, so mirrored events keep the old tenant if a member moves.
- **SEC-09 (LOW).** 10 high advisories, all build-time (`vite-plugin-pwa` ->
  workbox chain, `sharp`); none reachable at runtime.
- Verified clean: all 14 edge functions inventoried for auth+scoping (see the
  audit table); RLS enabled on every table; kid policies SELECT-only; the sole
  `dangerouslySetInnerHTML` is QR geometry from `uqr`; markdown has no
  `rehype-raw`; linkify forces https; no secrets committed (`.env*` never in
  git history; VAPID public key is public by design).

### Correctness (BUG)

- **BUG-01 (HIGH, money).** Monthly payments due on the 29th-31st drift
  permanently to the 28th: `addMonth` returns the clamped date and the caller
  feeds it back as the new anchor (`usePayments.ts:434,469,554,574`;
  `payment.ts:228`). Undo makes it worse (the original day is unrecoverable).
  The correct helper (`getDueDateInMonth`) already exists and is unused on that
  path.
- **BUG-01b (HIGH, money) - found independently by the test audit.** There are
  TWO recurrence engines that disagree: `expandPaymentOccurrences`
  (agenda/budget) chains `addMonth`, while `PaymentsPage` re-derives from the
  original day via `getDueDateInMonth`. Consequences: the same bill shows
  different occurrence dates on different screens, and overrides keyed on
  `overrideKey(id, occurrenceDate)` written from one surface are INVISIBLE to
  the other - a canceled instalment still shows on the dashboard and still
  counts in the projection. Third divergence: `getWeeklyOccurrencesInMonth`
  rewinds with no series-start floor, so it can emit an occurrence BEFORE the
  payment series begins. None of the four `date.ts` recurrence helpers has any
  test.
- **BUG-02 (MED, security-adjacent).** Kid PIN failure counter is
  read-modify-write (`kid-auth/index.ts:359-375`), so parallel guesses cost one
  strike instead of N - degrading the lockout the design leans on.
- **BUG-03 (MED).** `receipts`, `receipt_items`, `profiles`, `families` have no
  broadcast trigger and no `TABLE_INVALIDATIONS` entry, so receipt splits and
  profile/family edits never reach other members' open sessions (and produce
  avoidable PT409 claim conflicts).
- **BUG-04 (MED, also PERF-02).** `useBusyDays` passes `{}` to `useEventsList`
  believing an `enabled` gate exists; it does not, so every mounted DateField
  (12 forms) fetches the ENTIRE events table unbounded.
- **BUG-05/06 (MED).** Two rapid list-item adds can share a `sort_order`
  (`onMutate` and `mutationFn` compute it from different cache views); the
  20-PATCH drag reorder is non-atomic and its rollback is immediately
  overwritten by the `onSettled` refetch.
- **BUG-07 (MED).** Timetable editor's implicit saves swallow rejections on
  unmount/day-switch, silently discarding typed columns.
- **BUG-08/09/10/11 (LOW-MED).** Receipt backfill reports a false failure on a
  unique-violation race; undo does not restore a deleted reschedule override;
  `useBusyDays` ignores paid/paused payments and mishandles Feb-29 birthdays;
  `sanitizeDecimalInput` turns a pasted `1.234,56` into `1.23`.
- Verified clean: no UTC/local date bug anywhere (noon-anchoring used
  consistently); all 18 non-null assertions are guarded; `.or()` span-overlap
  filter correct; A/B week parity DST-safe; multi-day slicing correct.

### Performance (PERF)

- **PERF-01 (HIGH).** Every app foreground fires TWO unfiltered
  `invalidateQueries` (visibility handler + channel rejoin), and Danas mounts
  18 query keys -> ~19 requests per burst, ~38 per resume. Both invalidations
  also steamroll every deliberate `staleTime`, including `Infinity`.
- **PERF-02 (HIGH).** `useFirstSteps` keeps an unbounded `select("*")` on
  events alive forever just to answer "are there any events?", and
  `useBusyDays` does the same per mounted DateField (see BUG-04).
- **PERF-04 (MED).** Broadcast invalidations are not coalesced and the writer
  also receives its own; one "mark paid" writes 3-4 rows -> 4-5 refetches of
  the payments list.
- **PERF-05 (MED).** `gcal-sync` does 2 sequential DB round-trips PER event
  (`calendarSync.ts:181-183,263-276`): a first connect over a normal calendar
  is 1000-4000 sequential round-trips in one invocation, each firing a
  broadcast.
- **PERF-06/07/08/09 (MED-LOW).** Agenda scroll-spy does an O(days-scrolled)
  rect walk per frame over up to 365 unvirtualized day sections; Budget search
  fires 3-4 queries per keystroke (the ⌘K palette debounces, this does not);
  `usePaymentHistory()` fetches all-time history when the page already knows
  the month; `resolveWeekBlocks` rebuilds 4 lookup maps once per week (~53x).
- Verified clean: bundle composition (date-fns per-function, markdown/dnd-kit
  code-split, scanner lazy); all touch/scroll handlers passive+rAF; `useToday`
  is a shared singleton; no client-side N+1; `send-due-pushes` genuinely
  optimized.
